Executive summary

The central architecture is the right one: a persistent proxy owns each stable port, a process manager owns ephemeral backends, and a shared service layer coordinates health-gated replacement. The implementation is well tested for its size and the operator surfaces are unusually complete for a local tool.

Verdict: the product model is sound, but the pre-audit lifecycle was not fully transactional. A rejected deploy could leave the healthy process detached while the registry described the rejected build. Runtime evidence also shows accumulated operational debt: stale registrations, repeated health failures, session residue, and documentation that has drifted from shipped behavior. The highest-risk lifecycle, timeout, environment, security, and session-growth defects are repaired in this branch.

What the system is

Anito is best understood as a local production control plane for developer-owned services. It is not the hot-reload process itself. It gives other apps, browsers, tests, and agents a stable address while swapping the implementation behind that address.

Operator surfacesCLI, React dashboard, HTTP API, and MCP tools initiate deploy, status, logs, restart, stop, and setup workflows.
→
Shared control primitiveinternal/service coordinates registry, process lifecycle, health checks, proxy swap, watcher, receipts, logs, and notifications.
→
Stable runtimeinternal/proxy permanently owns consumer ports while internal/process starts services on ephemeral ports.

What is working well

  • The stable-port proxy is a clean, differentiated product primitive.
  • Health gating protects consumers from most bad starts.
  • Registry writes are atomic and multi-port data is backward compatible.
  • CLI lifecycle operations use the HTTP client, so they normally converge on the daemon-owned service layer.
  • Logs are available through HTTP/SSE rather than assuming filesystem access.
  • Focused Go coverage is strong across most internal packages, and the race suite passes.

Where the model leaks

  • Startup restore is duplicated in cmd/anito/main.go instead of owned by the service layer.
  • anito_setup performs orchestration and file mutation inside the MCP transport layer.
  • Multi-port handlers are swapped one entry at a time, despite documentation calling the group atomic.
  • Stateless MCP transport is paired with persistent session tracking, producing thousands of low-value handshake records.
  • The issue store is an event log, but the UI and docs often treat it like a bug tracker.

Ranked findings

P1 Fixed

Rejected deploys were not transactional

Redeploy staged new registry metadata and detached the healthy process before readiness was known. On candidate failure, the old process could continue serving but become untracked, while later restarts used the rejected binary or environment. A later successful deploy could leak the detached process.

internal/service/service.go, internal/process/process.go. Repaired with explicit candidate, detach, activate, restore, and drain primitives plus a real failed-redeploy integration test.

P1 Fixed

Consumer env files could override Anito-owned ports

env_file variables were appended after PORT, PORT_<NAME>, and ASP.NET Core port variables. Duplicate environment keys resolve to the last value, allowing an old fixed port in .env to defeat the ephemeral-port contract and cause health timeouts.

internal/process/process.go. Consumer variables now load first and Anito-owned values are appended last.

P1 Fixed

Partial MCP redeploys reset omitted service configuration

The documented name-and-path redeploy workflow rebuilt the service record from zero values, silently dropping args, env file, custom health policy, watch paths, restart policy, and config provenance.

internal/mcp/mcp.go. MCP redeploy now merges omitted registered fields by default and exposes replace_config: true for intentional full replacement.

P1 Fixed

Health checks could exceed their configured timeout

The readiness loop used http.Get without a request context. A backend that accepted TCP and withheld headers could block indefinitely despite health_check_timeout.

internal/service/service.go. Each attempt now receives a deadline bounded by the remaining overall timeout.

P1 Fixed

Toolchain vulnerabilities were reachable

govulncheck found 13 reachable standard-library and x/net vulnerabilities. The repository only declared Go 1.25.0 and was building with Go 1.25.6.

go.mod now pins toolchain 1.25.12 and updates x/net plus linked x/* modules. Post-repair scan: zero reachable vulnerabilities.

P2 Fixed

Lifecycle history never completed

Every start was appended with exit_code=-1, but no production path filled in the exit code or duration. The dashboard therefore displayed historical processes as currently running.

internal/registry/registry.go, internal/process/process.go. Starts are recorded and completed centrally by the process manager.

P2 Fixed

Session telemetry grew without a bound

Every session create/touch rewrote the entire JSON store. The live file reached 2,341 records and 508 KB, with 98% of entries never calling a tool.

internal/sessions/sessions.go. Writes are now atomic and the store keeps the 500 most recently active sessions.

P2 Fixed

Registry pointers and watcher debounce state escaped synchronization

Registry reads returned mutable internal pointers and maps. The watcher timer callback accessed shared debounce state from a separate goroutine. Both patterns were vulnerable to future data races even though the current race suite did not trigger them.

internal/registry/registry.go, internal/watcher/watcher.go. Registry values are deep-copied at boundaries and debounce state is synchronized with generation checks.

P1 Open

Daemon startup restore is serialized and outside the service layer

runDaemon opens proxies, starts processes, waits for health, updates registry state, and logs issues itself. Running services are restored one by one before the management API or MCP server starts. Startup latency can become the sum of multiple 15-90 second health timeouts, and the logic can drift from deploy/restart behavior.

cmd/anito/main.go is 952 lines and contains a second lifecycle orchestrator. This needs a tested Service.RestoreAll primitive and a bounded-concurrency rollout.

P1 Open

Multi-port “atomic” swap is not atomic across the group

SwapPorts validates all entries first, then stores each new handler independently. Requests arriving during that short loop can observe a mixture of old and new backends across named ports.

internal/proxy/proxy.go. Correct implementation requires a shared generation/routing snapshot, not more locking around individual stores.

P2 Open

Operational records lack lifecycle and ownership

The issue store supports append, list, source filtering, and clear-all. It has no fingerprint, occurrence count, acknowledgement, resolution, or link to a tracked bug. The service registry similarly has no explicit “archived” or “stale” state, leaving 17 failed entries mixed with active services.

internal/issues, GET /issues, and the live registry. This is why the system appears to have “a lot of bugs” without a reliable count of unique bugs.

P2 Open

Large transport and orchestration files blur ownership

Production files now include service.go at roughly 1,350 lines, main.go at 952, and mcp.go above 920. The size is a symptom: setup, runtime lifecycle, logs, case studies, crash recovery, and transport mapping share files and make focused testing harder.

7,593 production Go lines, 11,570 Go test lines, 466 Go tests. The test investment is good; the module boundaries should catch up.

P2 Open

Frontend and delivery automation have no executable safety net

The React app builds successfully but has no test script, component tests, accessibility checks, or browser smoke suite. No GitHub Actions workflow is checked in. The Go coverage gate had also drifted below three declared floors until focused tests were added in this audit.

internal/server/ui/package.json, absent .github/workflows, and scripts/coverage.

MCP review

The MCP concept is one of Anito's strongest product decisions. The current tool set covers the important operator loop, but transport code has accumulated business logic and the diagnostic responses were too thin.

AreaAssessmentRecommendation
Lifecycle toolsdeploy, services, status, logs, restart, rollback, stop, and remove map to the shared service layer.Keep this shape. Add typed error categories and consistent recovery hints rather than more narrow tools.
Status payloadsBefore this audit they omitted restart policy, health policy, crash state, and start history.Fixed Responses now include the operational fields agents need.
Redeploy semanticsThe common partial redeploy call previously cleared omitted registered settings.Fixed Omitted fields are preserved unless replace_config is true.
Setupanito_setup plans, writes files, patches source, and reserves ports inside internal/mcp.Move plan/apply into a shared setup application service. Expose it through MCP, HTTP, and CLI with identical dry-run output.
ParityHTTP has metrics, sessions, issue clearing, and streaming logs; MCP has setup, reserve, and case-study submission. CLI has a simpler local setup path.Define a capability matrix intentionally. Core operations should share primitives; not every presentation-only endpoint needs an MCP tool.
Session modelThe server is intentionally stateless, yet persistent sessions imply durable connection identity that does not really exist.Track client activity or tool-call cohorts, not “connected sessions,” unless the transport becomes stateful.
TestingMCP package coverage is 27.1% after this audit; most tool registrations are not exercised end to end.Add an in-process Streamable HTTP harness that initializes, lists tools, validates schemas, and executes every read-only tool plus isolated lifecycle fixtures.
Recommended MCP direction: prefer a smaller number of high-context tools over a proliferation of commands. A future read-only anito_diagnose could compose service status, doctor results, recent logs, matching issue fingerprints, and a safe next action through one shared diagnostic primitive.

Remediation plan

Phase 0
Completed
Protect the running service contract.
Land candidate rollback, deadline enforcement, port ownership, accurate lifecycle history, path validation, security updates, session cap, watcher synchronization, and regression tests.
Exit: race suite, coverage floors, UI build, and vulnerability scan pass.
Phase 1
Reliability
Move daemon restore into the shared service layer.
Build a two-phase restore primitive: register all listeners first, then restore binaries with bounded concurrency and candidate activation. Add a startup state model so liveness can respond while mutations wait for reconciliation.
Exit: restore time bounded by the slowest concurrency wave, dependency fixtures pass, no lifecycle code remains in main.go.
Phase 2
Control plane
Unify setup and diagnostics.
Create shared plan/apply and diagnose primitives. Map CLI, HTTP, dashboard, and MCP to the same request/result types. Introduce typed domain errors for not-found, invalid config, readiness failure, and conflict.
Exit: a parity contract test proves equivalent behavior across surfaces.
Phase 3
Operations
Turn logs into manageable operational records.
Add issue fingerprints, occurrence counters, first/last seen, acknowledge/resolve state, and an optional tracker link. Add explicit archive/prune flows for stale service registrations.
Exit: dashboard count represents unique active problems, not raw attempts.
Phase 4
Architecture
Make multi-port activation genuinely atomic.
Replace per-entry handler updates with one immutable routing generation referenced by every named listener. Split lifecycle, logs, setup, crash policy, and case-study concerns into focused application services.
Exit: concurrency test cannot observe mixed generations; production files have clear ownership.
Phase 5
Delivery
Add executable UI and release gates.
Introduce component tests for filters/actions/errors, Playwright smoke tests for service index and logs, accessibility checks, and CI for Go tests, race-critical packages, coverage floors, UI build, and govulncheck.
Exit: every pull request runs the same checks used in this audit.

Feature ideas - not implemented

These build on the current product without turning Anito into a cluster manager or cloud platform.

One-shot diagnose and repair planA read-only command/tool that combines status, doctor, recent logs, issue fingerprints, config provenance, and a proposed recovery sequence. Require explicit confirmation before any restart or file change.
Cold-start workspace onboardingUse the existing design work as a real setup surface: inspect repository, show service contract gaps, preview generated files and port allocations, apply, deploy, then graduate to the services index.
Service provenance and stale-state inboxShow which repo/worktree/config owns each registration, whether that source still exists, and offer “adopt,” “archive,” or “remove” instead of leaving failed rows indefinitely.
Dependency-aware restore groupsLet composite setups declare startup dependencies and health dependencies. Restore independent services concurrently and gate dependents without requiring general-purpose orchestration.
Typed activity streamPublish structured deploy, watch, restart, crash, restore, and issue-state events instead of parsing daemon log text. The dashboard and agents can consume one bounded event feed.
Local service aliasesOptional human-readable aliases such as my-api.anito.local would remove port memorization while preserving stable ports underneath. This needs careful macOS resolver design and should remain optional.
